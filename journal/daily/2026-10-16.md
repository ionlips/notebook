❯ Can you actually explain the technical work done to port to AMD?

Very little of the work was about AMD as such. The UMA model and the fairchem training code are plain PyTorch, and ROCm builds of PyTorch keep the torch.cuda interface. As a result, cuda devices, mixed precision and the nccl distributed backend all work unchanged, with RCCL (AMD's version of NCCL) underneath. No model code and no training settings were changed. The work went into four areas: the software environment, how jobs are launched, matching the run layout to LUMI's hardware, and the data.

1. Software environment (lumi/env.sh, lumi/env_build/)

- Container: LUMI wants Python environments inside containers, because thousands of small Python files are slow on its shared Lustre filesystem. The older LUMI PyTorch images are deprecated, so I used the LUMI AI Factory image: ROCm 7.0.2, PyTorch 2.10 for ROCm, and RCCL with the aws-ofi-nccl plugin for LUMI's Slingshot network.
- fairchem: fairchem-core 2.21.0 requires torch~=2.8. A plain pip install would replace the container's ROCm PyTorch with a CUDA build. I installed fairchem with --no-deps and its other dependencies separately.
- One-file venv: the whole venv (about 13,000 files) is packed into one squashfs image, uma-venv.sqsh, mounted at /user-software. Lustre then sees one file instead of thousands.
- Network and cache settings in env.sh:
  - RCCL is forced onto Slingshot through libfabric (the logs show NET/Libfabric).
  - FI_MR_CACHE_MONITOR=userfaultfd is set.
  - NCCL_SOCKET_IFNAME and NCCL_NET_GDR_LEVEL are deliberately left unset, because they're known to cause hangs with these ROCm 7 images.
  - MIOpen's kernel cache goes to node-local /tmp rather than Lustre.

2. Launching (lumi/lumi_run.sh, lumi/lumi_launch.py)

On MeluXina, fairchem -c … submitted its own Slurm job through submitit. That can't work inside the container, which has no sbatch or scontrol. So I split the launch in two:

- run.sh (one per case) keeps the original fairchem arguments and submits them with sbatch.
- lumi_run.sh runs on the host inside the allocation. It:
  - looks up the master node and port with scontrol;
  - sets a run ID that all ranks share;
  - starts one srun task per GCD inside the container;
  - pins each rank to the 7 CPU cores next to its GCD.
- lumi_launch.py runs on every rank and then calls fairchem's own SlurmSPMDProgram, the same code path submitit used. Before that it:
  - Fixes distributed setup. fairchem finds the master node with scontrol show hostnames. Inside the container that command fails silently, and fairchem then skips distributed setup, so every rank would train alone without any error. The fix passes the host-side MASTER_ADDR to fairchem.
  - Checks the rank layout. It confirms the node and rank counts in the config match what Slurm actually started.
  - Keeps the original log names. Logs are written as submitit named them (<jobid>_<rank>_log.out/.err), so the original check_throughput.py works unchanged.
  - Exits straight after training. This skips the step where PyTorch shuts down its communication, which is what hung the two long runs at 256 and 512 GCDs.

3. Matching LUMI's hardware (configs/.../cluster/lumi.yaml, run.sh)

- An MI250X has two dies (GCDs), and PyTorch sees each as a separate GPU with 64 GB. A node therefore has 8 "GPUs", against 4 A100s per MeluXina node.
- cluster=a100_slurm became cluster=lumi:
  - ranks per node: 4 → 8;
  - nodes = GPUs / 8;
  - 7 CPU cores and 6 data-loading workers per rank, because only 56 of the 64 cores are usable;
  - LUMI data and output paths.
- The core masks in lumi_run.sh follow LUMI's documented layout. Each GCD is wired closest to one specific group of 8 cores, and the first core of each group is reserved for the system.
- Other LUMI requirements in run.sh: --account is mandatory, and the default time limit is 1 minute, so every case sets its own.

4. Data and configs

- Training configs: uma_sm_direct_pretrain.yaml is unchanged. In uma_sm_conserve_finetune.yaml only the starting checkpoint path changed.
- Downloads: I downloaded the OMol25, ODAC25, OC25 and UMA checkpoint repositories with your Hugging Face token, plus the public OMat24 and OMC25 data.
- ODAC25 metadata: it ships without the metadata.npz file fairchem needs, so I generated it (tools/make_natoms_metadata.py).
- my_uma_small: rebuilt from the canonical_config.yaml saved in the zip's batch runs.
- my_uma: this wasn't in the zip. I built it as my_uma_small with 30× the training samples, sized to fit the budget.
  - Its validation sets are also 15× larger, because fairchem stops with "there are less batches than ranks!" once there are at least 64 ranks and too few validation batches.

5. Run layout

tools/make_runs.sh generates every run.sh in the original folder structure (000_batches, 001_UMA_PT, 002_UMA_FT, strong and weak), plus 256- and 512-GCD cases. LAUNCH=salloc ./run.sh runs a case interactively instead of through sbatch.

The README's "What changed compared with the zip" and "LUMI specifics" sections have the same material in short form, if you need it for the presentation.

❯ What questions should I ask about the original uma_training.zip. Should I ask for data, config files, etc.?

Yes, ask for both. The most important gap is the my_uma dataset config and the data behind it: I had to rebuild those myself, so the scaling numbers can't yet be compared like-for-like with the A100 runs. Here's what to ask, most important first.

1. Dataset configs and data (affects comparability)
- dataset/my_uma.yaml: this wasn't in the zip, and every strong/weak scaling run uses it. I built my own version (my_uma_small × 30 for training, × 15 for validation). Their real one changes the problem size, so it changes the scaling results.
- dataset/my_uma_small.yaml: I rebuilt it from the canonical_config.yaml files saved in the batch runs. Their original would confirm it.
- Exact data used for each dataset key, which I had to guess:
  - OMol25: was it the 4M training subset?
  - OMat24: was it the 1M subset?
  - OC25 under the oc20 key: was it the validation split or training?
  - ODAC25: was it the filtered validation sets?
  - OMC25: was it the validation set?
- ODAC25 metadata.npz: the download doesn't include it, so I generated it. Did they generate theirs the same way, or use a different source?
- Fine-tuning checkpoint: confirm it was uma-s-1p1.pt.

2. Software versions
- The exact fairchem-core version. I picked 2.21.0 because it's the newest release whose configs match their YAML files.
- Their environment file (pip freeze, conda environment, or module list): PyTorch, CUDA, NCCL.
- Their cluster/a100_slurm.yaml, if they changed it from the default (data-loading workers, timeouts, paths).
- Any NCCL or other environment variables they set on MeluXina.

3. Reference results (for an honest comparison)
- Their A100 strong/weak scaling logs. The zip only had the batch-size sweep logs, so I could compare one device against one A100 but not the scaling curves.
- Reference loss and validation metrics for a fixed configuration and seed. I checked that training runs and scales on LUMI, but I didn't check that the AMD runs produce the same accuracy as the A100s. A short side-by-side run would cover that.
- MeluXina node details: A100 40 GB or 80 GB, and the interconnect. This explains why fine-tuning at 1600 ran out of memory there.

4. Intent
- Which measure matters to them: time to finish training, or throughput?
- What final setup are they aiming for: how many GPUs, and which dataset size?
- Were the weak-scaling epoch rules (GPUs/2 for pretraining, GPUs/4 for fine-tuning) a deliberate choice?
- Did they ever see runs hang mid-training or fail to exit on MeluXina?

Of these, the dataset config is the one to get first: once you have my_uma.yaml and the matching data, rerunning a few key cases (for example 8, 64 and 200 GCDs) would give numbers you can put directly next to theirs.
